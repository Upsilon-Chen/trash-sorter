## 1.2 原型设计（功能细节）

**建议页标题**：界面原型与功能细节

### 三个页面（同一套视觉语言）
1. **控制台**：摄像头卡片（设备选择/预览/帧统计/抓拍）→ 识别结果卡片（类别+置信度表盘/多目标策略/分桶统计/下发历史）→ 模型卡片（权重/置信度阈值）→ 串口卡片（端口/连接/手动分拣/报文）
2. **数据标注**：图片列表（状态筛选 + **类别筛选**）→ 画布（画框/移动/删除/缩放）→ 增强设置 → 参考图采集
3. **记录中心**：分拣记录表（缩略图/判定/训练集标记/删除）→ 统计·训练集索引（可浏览、改类别、批量划分）

### 原型的可验证细节（答辩时演示这几个）
- **状态条五段**：`SYS / WS / CAM / MODEL / ESP32`，每段都绑定真实状态（断串口 ESP32 立刻变 OFF）
- **按钮可用性随状态变化**：未开摄像头时「开始检测」禁用并给 tooltip
- **失败可见**：串口未连接时手动下发 → 明确提示「串口未连接，无法下发分类指令」（后端 409）
- **切页不丢状态**：三个页面常驻，切页不重新枚举设备

## 1.3 数据库设计

**建议页标题**：数据库设计（记录与数据资产的沉淀）

### 为什么引入数据库
分拣结果原本只存在于「界面 + 日志」，无法统计、无法追溯、无法回流训练。数据库把「一次分拣」变成**可查询的资产**。

### 三张表（MySQL 8 / InnoDB / utf8mb4）

```
sort_records  一次下发一行（主表，轻量）
  时间 / 来源(auto·manual) / 类别 / 中文名 / 置信度 / bbox(JSON)
  / 桶位 / 角度 / 串口结果 / 原因 / 模型 / 会话
  / verified(pending·correct·wrong) / true_class
  / in_dataset / dataset_image_id
  索引：created_at, (class_name,created_at), (verified,created_at), (in_dataset,created_at)

sort_images   1:1 存图（大字段隔离）
  image_raw(原始无框帧，回流训练用) / image_marked(带框，证据展示) / thumb(320px)
  width/height/三个 size/sha1

dataset_images  训练图索引（文件仍以磁盘为准）
  path(唯一) / class_name / split(train·val·test·unsplit) / source / record_id
  / width/height/sha1 / labeled / label_path
```

### 三个设计决策（体现取舍）
| 决策 | 理由 |
| --- | --- |
| 图片存 BLOB 但**拆到独立表** | 列表查询永不触碰大字段；缩略图单独接口 + 一天缓存 |
| 三张图分开存 | `raw` 干净可直接回流训练；`marked` 是证据；`thumb` 让列表快 10 倍 |
| 训练集**只索引不托管** | YOLO 训练要目录树，文件仍是事实来源；DB 只提供分类/划分/标注状态查询 |

体积控制：JPEG 质量 75 + 长边 1280 → 单条约 180 KB；保留 30 天，后台每 6 小时清理一次。

## 1.4 概要设计

**建议页标题**：概要设计（分层与关键机制）

### 分层
```
表现层  React 三页面（常驻切换）
接口层  FastAPI 33 个 REST + /ws
业务层  camera / detector / pipeline / serial / annotator / augmenter / recorder
数据层  classes.json（映射）+ MySQL（记录）+ 磁盘（图片/权重/数据集）
设备层  OpenCV(dshow) / pyserial / ESP32 固件
```

### 四个关键机制
1. **线程模型**：摄像头抓帧线程、检测流水线线程、串口读线程、记录写库线程，彼此用锁/队列解耦；**任何 IO 都不许在事件循环里做**。
2. **事件总线**：后台线程 → `EventBus.emit`（线程安全）→ asyncio 队列 → WebSocket 广播；记录器只需包装 emit 即可挂钩，**流水线零改动**。
3. **降级链**：数据库不可用 → 记录功能关闭（其余照常）；串口不可用 → 检测照跑不下发；摄像头异常 → 自动重连 + 占位图。
4. **配置外置**：类别映射、冷却时间、串口参数、数据库连接全部在 `classes.json` / `settings*.yaml`，改行为不改代码。

## 1.5 系统结构图（模块划分 / 接口 / 高内聚低耦合 / 重要算法）

**建议页标题**：系统结构图与模块接口

### 模块依赖（单向、无环）

```
            ┌──────────────── 前端（React）────────────────┐
            │  ConsolePage  AnnotatePage  RecordsPage      │
            └───────┬─────────────┬──────────────┬─────────┘
                    │ REST/WS（只依赖接口，不依赖实现）      │
            ┌───────▼─────────────▼──────────────▼─────────┐
            │                api/main.py（编排层）          │
            └──┬────────┬────────┬────────┬────────┬───────┘
               │        │        │        │        │
        camera │ detector│ pipeline│ serial │ annotator/augmenter/recorder
               │        │        │        │        │
            OpenCV   ultralytics 队列+锁  pyserial   MySQL / 磁盘
```

| 模块 | 对外接口（契约） | 内聚点 | 耦合方式 |
| --- | --- | --- | --- |
| `camera` | `open/close/get_frame/get_jpeg/frames/status` | 设备生命周期与锁 | 只被 pipeline/记录器按帧调用 |
| `detector` | `load/predict/status` | 模型与推理 | 输入 ndarray，输出 Detection 列表 |
| `pipeline` | `start/stop/manual_sort/snapshot` | 一次分拣的完整决策 | 通过构造注入 camera/detector/serial |
| `serial` | `connect/disconnect/send_sort/status` | 协议与连接状态 | 只吃 (class, slot, angle) |
| `recorder` | `on_event/status` | 记录与图片编码 | 只订阅事件，不改别人状态 |
| `records_api` | 11+5 个 REST | 记录的读写与判定 | 只依赖 db 层 |

**低耦合的两个具体证据**
1. `pipeline.py` 不知道数据库存在——记录通过 `emit` 事件旁挂，删除记录模块对主流程零影响。
2. 类别映射全在 `classes.json`：新增一类垃圾只改配置，`pipeline`/`serial` 都不动。

### 重要算法（3 个）

| 算法 | 位置 | 说明 |
| --- | --- | --- |
| **多目标选择** | `pipeline._select_target` | 四种策略：`priority`（按配置优先级）/`largest`（面积最大）/`confidence`（置信度最高）/`hold`（保持上一目标，避免犹豫） |
| **冷却与同帧抖动抑制** | `pipeline._dispatch` | 按桶维度冷却（可被归类覆盖）+ 连续 N 帧确认，避免同一物体反复倾倒 |
| **增强坐标变换** | `augmenter.py` | 旋转 90/180/270 与翻转时**同步变换 bbox**：`(x,y)→(1−y,x)`、`(x,y)→(x,1−y)` 等，保证标签与像素严格对齐 |

## 1.6 编码（编码规约与设计覆盖）

**建议页标题**：编码实现（规约先行，覆盖设计）

### 编码规约（组内约定，答辩可逐条展示）
| 规约 | 落地方式 |
| --- | --- |
| 类型先行 | 后端全量类型注解 + `py_compile` 卡口；前端 `strict` + `tsc` 零错误才构建 |
| 单一职责 | 每个 service 只做一件事；`main.py` 只做编排，不写业务 |
| 配置外置 | 阈值/冷却/端口/连接串不进代码 |
| 错误分级 | 业务错误 → 4xx + 可读中文 detail；系统错误 → 5xx；**两种情况都不崩** |
| 日志统一 | `时间 \| 级别 \| 模块 \| 消息`，禁用裸 `print` |
| 并发纪律 | **IO 不进锁**；所有取锁带超时；长任务进独立线程/`to_thread` |
| 提交规范 | 一次改动一个主题；提交信息写「根因 + 修法 + 验证」 |

### 典型 Bug 跟踪表（12 个，答辩直接展示这张表）

| # | 现象 | 根因 | 修法 | 验证 |
| --- | --- | --- | --- | --- |
| B1 | 所有列表一直转圈 | 浏览器同域 6 连接被多条 MJPEG 占满，溢出请求无限排队 | MJPEG 单流策略（新流顶掉旧流） | 5 条并发流收敛为 1 |

# 二、AI 工具的使用（按实际使用范围）

**建议页标题**：开发中 AI 工具的实际应用

> 原则：**工具做什么、我们做什么**，边界要清楚，不夸大。

### 2.1 编码阶段

| 场景 | AI 参与方式 | 人工把关 |
| --- | --- | --- |
| 后端接口与服务的初稿 | 生成 FastAPI 路由、服务骨架、类型注解 | 逐行评审；接口契约与字段命名按项目规范改写 |
| 数据库接入 | 生成 SQLAlchemy 模型、会话工厂、CRUD 接口 | 决定拆表策略（BLOB 独立表）、索引与降级方案 |
| 前端组件 | 生成面板/表格/抽屉等结构 | 统一到项目自带视觉语言（`rhine.css`），禁止引入第二套 UI 风格 |
| 缺陷定位 | 协助读日志、写复现脚本、对比 A/B 实验 | **根因结论必须由实测数据支撑**（如 B1 靠"卡住期间请求有没有到后端"定性） |
| 脚本工具 | 生成截图、进度监视、批量回填等脚本 | 运行前审权限范围（只读/写库/删文件） |

**边界（很重要）**：AI 写的代码 100% 经过人工评审与实跑验证；**没有一次是"生成即合并"**。
例如 `LONGBLOB(mysql_display_width=…)`、`include_router` 位置、`String.Replace` 重载这些坑，
都是实测报错才定位到的，说明验证环节不可省。

### 2.2 文档与测试阶段

| 产出 | AI 参与 | 人工补充 |
| --- | --- | --- |
| `README.md`（架构/接口/FAQ） | 整理与改写 | 业务判断、阈值与硬件相关的取舍 |
| `docs/ARCHITECTURE.md` | 结构与改动指引 | 项目约定（并发纪律、路由注册位置等踩坑总结） |
| 测试书（85 条用例） | 按模板批量生成用例文本与统计脚本 | 判定哪些能实测、哪些必须标"待执行" |

| 答辩材料 | 结构整理 | 所有数字与结论的复核 |

### 2.3 效率上的实际收益（可量化）
- 测试书从「手写 85 条 + 手工截图」变为**脚本生成**：用例文本 1 次生成、截图与编号自动完成
- 缺陷定位：日志 + A/B 实验把「猜」变成「测」，B1~B6 平均定位时间从小时级降到分钟级

## 3.2 系统能力边界
- **单件分拣**：一次倾倒只能走一个方向，两件不同大类的垃圾必然有一件被分错 → 已用「多目标策略」把限制显式化，但没解决
- **透明/反光物体**：玻璃杯与背景差异小，背景差分易漏框，需人工补标
- **机位与光照敏感**：参考图依赖固定环境，换位置要重拍
- **无鉴权**：仅适合本机/内网
- **串口协议无重传**：丢包场景无可靠性保证

## 3.3 过程与团队协作上的遗憾

| 方面 | 具体表现 | 后续做法 |
| --- | --- | --- |
| 需求变更 | 中途加入"分拣记录入库"需求，导致数据库设计推倒重来一次（第一版把图片与记录放同一张表） | 需求变更先出 1 页「影响面清单」（表结构/接口/前端/测试）再动手 |
| 文档滞后 | 功能做完才有文档，README 与 ARCHITECTURE 都是后期补的 | 约定「接口变更 → 当天更新 `ARCHITECTURE.md` 的模块接口表」 |
| 评审缺失 | 部分改动"能跑就合并"，后期集中暴露（如路由注册位置、缓存头） | 每次合并前的检查清单：构建通过 / 关键接口实测 / 是否影响既有用例 |
| 并行冲突 | 两人同时改同一面板，靠口头协调 | 按模块划分所有权 + 小步提交 |
| 测试前置不足 | 大量验证在功能完成后才补，导致返工 | 用例先行：需求确认时同步写 3~5 条验收用例 |
| 硬件依赖 | 舵机/串口相关用例必须实机，回归成本高 | 做「串口回环模拟器」把硬件依赖从回归链里摘出来 |

## 3.4 展望（若再有一个迭代）
1. **数据闭环自动化**：记录 → 误检样本自动进标注队列 → 增量训练 → 指标对比（现在只做到"人工点一下回流"）
2. **多桶并行**：硬件升级为多托盘/机械臂后可支持多件分拣
3. **指标看板**：把记录中心的统计扩展成「按天/按类别的准确率与失败率趋势」
4. **可移植**：用 SQLite 单文件 + 便携版 Python 做一台"拷走就能跑"的演示机
